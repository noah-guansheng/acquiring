GET STARTED

接入前，先确认这几件事

商户服务端创建与查询支付，买家在平台收银台完成操作；凭据、金额与最终支付结果都由服务端管理。

INTEGRATION FLOW

完成第一笔接入

先确认生产凭据、商户开通、MID、渠道及可用支付方式，再连接商户服务端与买家页面。

  1. 服务端创建收银台订单。持久化订单与 Idempotency-Key，签名调用 POST /checkout-sessions，使用 amount / currency / clientOrderId，保存返回的 session.id。
  2. 买家打开平台收银台。使用 https://checkout.saferoute.global/checkout/?sessionId=<session.id>，仅交给本订单买家；API 凭据留在服务端。
  3. 服务端确认结果。签名查询原 Session，读取其 paymentIntentId 后查询对应 Intent，或处理已验签的支付结果通知；核对原订单、金额、币种与兼容支付成功结果后履约。Session complete 不能单独确认收款，也不等于平台 Payment CAPTURED。
浏览器返回只用于体验页面跳转、关窗或前端完成提示均不能确认收款。处理中、超时、未知结果应继续确认原支付，避免创建第二笔。

完整服务端示例

保存为 create-checkout-session.mjs，使用 Node.js 18+，无需安装依赖。通过环境变量设置凭据、持久化的原幂等键和订单号；正文只序列化一次。运行示例会发送正式建单请求，仅在平台确认商户与渠道已开通后使用。示例本身不代表已完成线上付款验收。

Node.js · create-checkout-session.mjs
import crypto from "node:crypto";

const origin = "https://api.saferoute.global";
const checkoutOrigin = "https://checkout.saferoute.global";
const { VCC_ACCESS_KEY_ID, VCC_SECRET_KEY, VCC_MERCHANT_CODE,
  VCC_IDEMPOTENCY_KEY, VCC_MERCHANT_ORDER_ID } = process.env;
if (![VCC_ACCESS_KEY_ID, VCC_SECRET_KEY, VCC_MERCHANT_CODE,
  VCC_IDEMPOTENCY_KEY, VCC_MERCHANT_ORDER_ID].every(Boolean)) {
  throw new Error("请在服务端设置凭据、原订单号和持久化的幂等键");
}

export const rfc3986 = value => encodeURIComponent(value)
  .replace(/[!'()*]/g, c => "%" + c.charCodeAt(0).toString(16).toUpperCase());

export function canonicalQuery(entries) {
  return entries.map(([k, v]) => [rfc3986(k), rfc3986(v ?? "")])
    .sort(([ak, av], [bk, bv]) => ak === bk
      ? (av < bv ? -1 : av > bv ? 1 : 0)
      : (ak < bk ? -1 : 1))
    .map(([k, v]) => k + "=" + v).join("&");
}

export function signRequest({ method, path, queryEntries = [], rawBody = "",
  idempotencyKey, timestamp = String(Math.floor(Date.now() / 1000)),
  nonce = crypto.randomBytes(16).toString("hex") }) {
  const query = canonicalQuery(queryEntries);
  const bodyHash = crypto.createHash("sha256")
    .update(Buffer.from(rawBody, "utf8")).digest("hex");
  const canonical = [timestamp, nonce, method.toUpperCase(), path,
    query, bodyHash].join("\n");
  const signature = crypto.createHmac("sha256", Buffer.from(VCC_SECRET_KEY, "utf8"))
    .update(Buffer.from(canonical, "utf8")).digest("hex");
  const headers = {
    "X-Access-Key-Id": VCC_ACCESS_KEY_ID,
    "X-Merchant-Code": VCC_MERCHANT_CODE,
    "X-Vcc-Timestamp": timestamp,
    "X-Vcc-Nonce": nonce,
    "X-Vcc-Signature": signature
  };
  if (rawBody) headers["Content-Type"] = "application/json";
  if (idempotencyKey) headers["Idempotency-Key"] = idempotencyKey;
  return { url: origin + path + (query ? "?" + query : ""),
    method: method.toUpperCase(), headers,
    ...(rawBody ? { body: rawBody } : {}) };
}

// 首次请求前保存这个正文；重试复用相同正文和原幂等键。
// 仅在平台确认生产商户与渠道已开通后运行。
const rawBody = JSON.stringify({
  amount: 1000, currency: "usd", clientOrderId: VCC_MERCHANT_ORDER_ID
});
const { url, ...init } = signRequest({ method: "POST",
  path: "/open/v1/acquiring/checkout-sessions", rawBody,
  idempotencyKey: VCC_IDEMPOTENCY_KEY });
const response = await fetch(url, { ...init, signal: AbortSignal.timeout(15000) });
const result = await response.json();
if (!response.ok || result.code !== "0") {
  throw new Error("HTTP " + response.status + "; code=" + result.code +
    "; traceId=" + result.traceId);
}
const session = result.data;
if (typeof session?.id !== "string" || !session.id) {
  throw new Error("创建响应缺少 Session ID，请保留原订单并核查请求结果");
}
const checkoutUrl = new URL("/checkout/", checkoutOrigin);
checkoutUrl.searchParams.set("sessionId", session.id);
const checkoutHref = checkoutUrl.href;
// 持久化 session.id，将 checkoutHref 仅交给本订单买家。
console.log({ sessionId: session.id, status: session.status });
// 超时不等于失败：用原订单/幂等键重试或签名查询，每次使用新 nonce。

AUTHENTICATION

鉴权与签名

本文商户 Open API 均使用 HMAC-SHA256。Secret 只保存在商户服务端，不放入 HTML、浏览器、URL 或客户端日志。

请求头要求内容
X-Access-Key-Id必填平台分配的 ACQUIRING AccessKeyId。
X-Merchant-Code必填与凭据绑定的商户编码一致。
X-Vcc-Timestamp必填Unix 秒的普通十进制整数，不传毫秒。
X-Vcc-Nonce必填[A-Za-z0-9._~-]{16,128}；每次 HTTP 请求使用新值，包括重试。
X-Vcc-Signature必填64 位小写十六进制 HMAC-SHA256。
Idempotency-Key写操作必填非空，长度不超过 128 字符；业务动作重试复用原值。
Content-TypeJSON 时application/json，UTF-8 编码。

生产收单凭据绑定一个商户、一个 MID、LIVE 环境及操作 scope，请求不能改选归属。时钟偏差默认容忍前后 10 分钟，实际以接入配置为准；时间解析为整数后以十进制文本签名。

六行 Canonical Request

依次用五个 LF（\n）连接，末尾不加换行。无 query 保留第五行空行；路径不含域名和问号。

Canonical · 顺序固定
timestamp_epoch_seconds
nonce_original_value
HTTP_METHOD_UPPERCASE
/open/v1/acquiring/checkout-sessions

signature = hexLower(HMAC-SHA256(UTF8(SecretKey), UTF8(canonical)))。Secret 是 UTF-8 文本 key，不做 hex 解码；输出使用 hex，不使用 Base64。

查询串规范化

  1. 取得解码后的全部 key/value，保留重复项与空值；已有 URL 可用 [...new URL(url).searchParams.entries()]。原 query 的 + 解码为空格，字面加号应传 %2B。
  2. 分别用 UTF-8 RFC 3986 编码：空格 %20，星号 %2A，~ 不编码。
  3. 按编码后的 key、再按编码后的 value 升序排序，完全重复项仍保留，以 key=value 和 & 连接。发送相同参数。
规范化示例 · 重复参数不合并
输入 entries:
[["z","two"],["z","one"],["name","a b"],["star","*"],["unicode","汉 字"]]

canonicalQuery:
name=a%20b&star=%2A&unicode=%E6%B1%89%20%E5%AD%97&z=one&z=two
签名覆盖实际发送的原始 body签名后不得重新 stringify、改变空白或加末尾换行。空 body 与 {} 不同；空 body SHA-256 为 e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855。完整函数见快速开始。

通用约定与接口目录

请求和响应使用 JSON、UTF-8 与 camelCase。HTTP 状态和字符串业务码共同表示调用结果。

金额、时间与空值

USD 10.25 传整数 1025；兼容 Session / Intent 的 amount 同样为美分。业务时间使用 ISO 8601；API 签名时间为 Unix 秒，Webhook 签名时间为 Unix 毫秒。现代响应的可空属性可能省略，兼容 Map 响应可保留 null。

幂等与不确定结果

同一业务动作保持原 Idempotency-Key、method/path/query/body；每次重试更新 timestamp、nonce 和 signature。同键异参或仍处理中可能返回 409 / 40904。超时或 5xx 先确认原资源或用原键重试，不换键再次建单。

分页结构

把返回的 nextCursor 原样续传；为空表示无下一页。不同接口游标不互通，不解析或自行递增。

COMPATIBILITY API

Checkout Session

通过 Session 创建收银台订单，使用 amount、clientOrderId 与小写状态；字段和状态与平台 Payment 分别处理。生产受理须先由平台确认商户及渠道开通。

POST/open/v1/acquiring/checkout-sessionspayments:write · Idempotency-Key
字段类型 / 必填约束
amountinteger · 必填1–99,999,999，美分。
currencystring · 必填usd。

PATCH/open/v1/acquiring/checkout-sessions/{id}payments:write · Idempotency-Key

仅允许 amount 与 expiresAt，至少一项，约束与创建相同。仅 open 可更新，否则 409 / 40916；示例：{"amount":1200}。

Session 与 Intent 分别确认常见 Session 状态为 open / complete / expired / canceled；没有通用 failed Session 终态承诺。Session complete 不等于平台 Payment 的 CAPTURED。兼容接入结合服务端查询与已验签完成通知确认原订单，必要时读取返回的 paymentIntentId。

EVENT DELIVERY

Webhook 通知

配置 HTTPS 接收地址、订阅与独立 Webhook Secret。通知 Secret 与 API Secret 分别管理；端点按商户、MID 与环境配置。

投递请求头约定
Content-Typeapplication/json; charset=utf-8
X-Vcc-Event-Id稳定事件 ID，必须与 body.id 一致。
X-Vcc-Webhook-Key-Id选择当前或轮换宽限期内密钥；旧密钥宽限默认 48 小时，以接入配置为准。
X-Vcc-TimestampUnix 毫秒。
X-Vcc-Signaturet=<timestampMillis>,v1=<64位小写hex>；t 须等于上方时间头。

先验签，再解析

签名消息为 UTF8(timestampMillis + "\n") || exactRawBodyBytes，使用通知 Secret 的 UTF-8 字节做 HMAC-SHA256 key。严格解析签名格式，检查时间窗并恒时比较。本契约不使用 nonce；验签前不得 JSON.parse 后重新 stringify。

Node.js · 原始 Buffer 验签
import crypto from "node:crypto";

// rawBody 是 HTTP 原始 Buffer，在 JSON 解析中间件之前获取。
// secret 按 X-Vcc-Webhook-Key-Id 从服务端配置的密钥集合选择。
export function verifyWebhook(rawBody, secret, timestamp, signature, now = Date.now()) {
  if (!Buffer.isBuffer(rawBody) || typeof timestamp !== "string" ||
      typeof signature !== "string" || typeof secret !== "string" || !secret) return false;
  const parts = /^t=([0-9]+),v1=([0-9a-f]{64})$/.exec(signature);
  if (!parts || parts[1] !== timestamp || !/^[0-9]+$/.test(timestamp)) return false;
  const millis = Number(timestamp);
  // 5 分钟是本接收端建议窗口，按双方接入约定设置。
  if (!Number.isSafeInteger(millis) || !Number.isFinite(now) ||
      Math.abs(now - millis) > 5 * 60 * 1000) return false;
  const expected = crypto.createHmac("sha256", Buffer.from(secret, "utf8"))
    .update(Buffer.from(timestamp + "\n", "utf8"))
    .update(rawBody).digest();
  return crypto.timingSafeEqual(expected, Buffer.from(parts[2], "hex"));
}
// 通过后再 JSON.parse，检查 id 与 X-Vcc-Event-Id 一致、version、type、
// environment、MID 和订单归属；幂等持久化成功后快速返回 204。

接收、去重与重投

  1. 验签并检查事件 ID、版本、环境、MID 与订单归属，以 event.id 幂等持久化。
  2. 持久化成功后快速返回任意 2xx（建议 204 空 body）；重复已接收事件仍返回 2xx，耗时履约异步执行。
  3. 容忍重复、延迟与非按序抵达。重投复用同一事件 ID / body，投递时间戳和签名可变化。
接收结果投递行为
2xx已确认接收。
408 / 429 / 5xx可按退避重试；默认首投加 3 次重试，配置可变。
其他非 2xx HTTP不自动重试，修复接收端后联系平台核查。
超时 / 网络结果未知不盲目自动重复；查询原支付，必要时联系平台核查通知。

错误处理与重试

保留 traceId、资源 ID、HTTP 状态和字符串业务码以便排查；不记录凭据、签名、checkout token 或完整敏感 body。

READY TO INTEGRATE

接入检查清单

生产接入前确认商户与渠道开通、签名规则、订单状态及异常处理。

  • 凭据类型、商户、MID、环境与操作 scope 已确认。
  • 商户生产开通、渠道与可用支付方式已确认。
  • 签名覆盖重复 query、空格、中文、空 body 与 JSON。
  • 每次 HTTP 新 nonce；重试保持原键与原正文。
  • 金额使用整数美分，订单与资源 ID 已保存。
  • 以 Session ID 构建平台收银台地址，仅交给对应买家。
  • 履约前查询原 Session / Intent 或验签通知，核对订单、金额、币种与支付结果；不单凭 Session complete。
  • 超时、5xx、409 处理中均确认原交易，避免重复支付。
  • Webhook 原始 Buffer 验签，检查 ID、版本与归属。
  • 持久化去重，重复事件返回 2xx，并容忍乱序。
  • 日志不含凭据、签名、checkout token 或敏感 body。
  • 生产 LIVE 凭据与受理范围已确认，线上验收由平台另行完成。
